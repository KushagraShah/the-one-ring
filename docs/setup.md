# Setup and current limitations

## Local development

Use Node.js 24 or newer (`.nvmrc` selects 24). Copy `.env.example` to `.env.local` and fill in the Supabase project URL and **publishable** key from the Supabase project's Connect/API Keys settings. `.env.local` is ignored by Git. Run `npm install` followed by `npm run dev`, then open the URL printed by Vite. Restart Vite after changing environment variables. `npm run build` checks TypeScript and creates the production bundle; `npm run preview` serves that bundle locally. `npm run test:config` checks deployment configuration validation.

The app version appears at the bottom of Settings and is sourced from `package.json`; keep `package-lock.json` in sync. The owner requires every pushed change to have a version number, normally a patch increment. A tag or GitHub Release remains a separate action.

`npm run test:browser` runs Playwright at phone width against a fake Supabase endpoint, not the real project. Install Chromium with `npx playwright install chromium`, or set `CHROMIUM_PATH` to an existing Chromium executable. The Pages workflow installs Chromium and runs these interaction tests before deployment; this does not replace real Android or live Supabase testing.

## Supabase authentication

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in `.env.local`. Only the current `sb_publishable_…` key format is supported; secret/service-role keys and legacy JWT keys are rejected. If configuration is missing or invalid, sign-in is disabled with a clear message and demo mode remains available.

These values are public browser configuration: Vite embeds `VITE_` values in the downloadable website even if they are stored as GitHub Secrets. Never put a Supabase secret/service-role key, database password, or access token in a `VITE_` variable. Database tables must be protected with RLS, not by hiding the publishable key.

In the Supabase dashboard, enable email/password authentication. Under Auth URL settings, set the Site URL to the deployed URL and allow redirect URLs for the deployed app and local preview (for example, `http://localhost:5173/`). Check email confirmation settings and delivery limits. The owner can disable signup after onboarding and temporarily enable it for a trusted user. First sign-in requires connectivity.

The online-only version requires migration `202611070004_online_workouts.sql`; the Activity/history changes additionally require `202611070005_history_client_guard.sql`. The owner reported applying both on 2026-11-07; live guard behavior has not been independently tested. For any other project, review the [migration runbook](supabase-migrations.md) and verify the target and existing schema before applying SQL. The `v0.2.0` tag uses the older local/manual-sync path.

Account workspaces load from Supabase into memory; changes are saved through a revision-checked transaction. A visible saving indicator remains until Supabase confirms all pending changes. Failures block further editing and offer retry, export of the unsaved in-memory state, or discard and reload. A stale revision requires export or reload. Closing the page before a failed or pending save is confirmed can lose that change. Drafts and unconfirmed edits are not durable. Existing local or old sync data is not automatically imported. Demo is separate in memory and resets on refresh. Supabase Auth may persist its session, and theme preferences use browser storage. Live Supabase isolation, real-device handling and backup recovery remain unverified; export backups and do not rely on this preview as the sole copy.

### Backup and restore

Settings can export a JSON copy of the current in-memory workout workspace, including exercises, routines, cycle progress, workout history, and confirmed in-progress session data. It does not include credentials, appearance preferences, routine drafts, or unconfirmed result edits. The file contains private workout data; keep it somewhere safe. Export while a save is pending or has failed captures the current in-memory state, which may not yet be on the server.

Restore checks the file and its online record identifiers before asking to replace the current workspace. It then saves the replacement to the current account using the normal revision-checked transaction; wait for the saving indicator to disappear. On a failed save, keep the page open and retry, or export the unsaved state. Demo restore lasts only until refresh. The owner reported successfully exporting, deleting a routine day and restoring; this does not establish every failure or recovery scenario. Fake-server browser tests cover export, validation, failed restore/retry and reload. Backups and the server have 10 MB limits; near-limit files may be rejected by the server after encoding.

## GitHub Pages

The workflow in `.github/workflows/deploy.yml` builds and deploys pushes to `main`. In repository settings, select **GitHub Actions** as the Pages source. Under **Settings → Secrets and variables → Actions**, add repository variables (or secrets if preferred) named `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, using the same public values as local development. The workflow reads a secret first if both exist under the same name, otherwise the variable. Add the configuration **before pushing or rerunning** the workflow; it fails early and leaves the previous deployment in place if configuration is missing or invalid. A change to a variable or secret requires a new workflow run to rebuild the static site.

The expected URL is `https://kushagrashah.github.io/the-one-ring/`; add it to Supabase's redirect allow list and check the Pages deployment workflow. The relative Vite base supports the project path and local preview.

The owner removed Supabase's separate GitHub integration after it attempted to apply already existing tables. This does **not** disable the GitHub Actions workflow that deploys the frontend to Pages. Database migrations must be tracked and handled separately; see the [migration runbook](supabase-migrations.md).

## Current preview

The overhaul branch separates the shared launcher (`src/app/`), workout (`src/workout/`) and habit tracker (`src/habits/`). Habit tracking is a local preview: demo habits are temporary, and signed-in habit storage requires the new migration 006, which has not been reported applied to the owner's project. See [migration guidance](supabase-migrations.md) before applying SQL. The launcher and each mini-app remain independently accessible on load failure; account workout and habit data stay in separate revision-checked stores. Real Supabase and phone testing remain outstanding.

Demo mode starts with fictional workouts, exercise results and habits spanning recent weeks so that history and insights can be explored immediately. Examples are marked in the mini-apps and reset when the demo is restarted or the page is refreshed. They are generated only for demo mode and never automatically imported into an account. Exported demo backups contain the fictional data and should not be restored into an account unless that replacement is intentional.

Habit Tracker provides fixed/flexible schedules, date-effective schedules and criteria, local-date outcome entry and correction, notes, undo, a seven-day correction view, catch-up, editing, pauses, archive and deletion. Weeks affected by a pause or skip are labeled as not judged against the flexible target. Schedule and criteria drafts are not durable. Habit saves replace a single JSON habit workspace with a 10 MB server limit; large histories and real-service behavior need assessment.

The local Insights view shows fixed-habit performance and coverage separately, monthly fixed results and flexible recorded activity, a month day-picker, eight weeks of results, per-habit recorded history and success/engagement streaks. Flexible weekly targets are judged only for completed, full active weeks with one unchanged flexible schedule and no pause or skip; excluded weeks do not break weekly streaks. Calendar-month flexible activity is counted by outcome rather than splitting weekly targets across months. Archived habits are excluded from summary denominators and streaks because archive dates were not captured; their recorded outcomes remain accessible. Ranking uses at least three scored fixed outcomes, and the workload prompt is a clearly labeled heuristic, not a judgment. Historical statistics depend on saved schedules and active dates; changing dates can change derived results. The new views need owner phone and real-service review.

Settings exports timestamped workout-only, habit-only and full-app JSON backups. Workout restore accepts earlier workout backups; habit and full restores are separate formats. Full restore validates both sections first, then saves each mini-app separately: it is **not atomic** and a failure can leave only one restored. Follow the save/error indicators and export before recovery. The full backup includes workouts and habits, not authentication credentials or browser appearance preferences. Demo restore remains temporary.

The app has demo mode, accent colors, an exercise library and multiple routines, balanced day suggestions, rotations, three-set strength and cardio logging, workout/exercise history, and JSON export/restore. Workouts shows the suggested day and first exercise near the top. During a workout, the focused exercise shows setup and up to three recent results; previous/skip/next controls navigate the session, skipping advances to the next exercise, and the last exercise offers a return to the first. An exercise may be replaced or added for today without changing the routine. There are no session move-earlier/later controls; previously reordered sessions and history remain readable. Setup notes use a multiline editor and preserve text including Markdown syntax. Leaving a workout keeps confirmed results for resumption; cancelling it explicitly discards the session. Strength entry offers shared weight adjustments and rep presets, with custom set fields available. A confirmed log is locked until edited; the workout finishes automatically when every exercise is completed or skipped. Completed results and notes can be edited in Activity, including older workouts; adding an extra exercise after automatic completion is not yet supported. Unconfirmed result edits stay in memory while navigating the session and are not saved until the tick; leaving warns before discarding them. Notes are saved separately. Backups receive structural validation before restore, but recovery under storage failures and browser/device changes has not been tested end to end. The sample routine and initial demo progress are illustrative. New history records use stable exercise IDs; older name-based records get best-effort linking. Older ambiguous names cannot be recovered automatically.

In **Workout Tracker → Build routine**, choose a routine, expand a day, and edit or reorder its exercises using the up/down controls. Changes are a temporary draft until **Save changes**; leaving warns before discarding, but drafts are not durable across a browser crash. An active workout blocks saving or switching routines; it can be cancelled from the builder without discarding the draft. Create an exercise cycle from an exercise, choose its variants and one or more days, or add an existing cycle to another day. The cycle editor indicates whether each selected day uses an existing exercise slot or adds a new one. All linked days share progress. During a workout, choose a different member using the dedicated **Exercise cycle** selector; completing that member counts toward the cycle. The separate ordinary replacement and extra-exercise controls do not count toward it, even if the chosen exercise happens to be a member. Completing A then choosing C out of order leaves B as the next suggestion; once every variant has been performed, the cycle starts again. Repeating an already-accounted variant or skipping does not advance it. Cycle progress is committed when the workout is finished, not separately when a log is ticked; cancelling a workout leaves it unchanged. Existing in-progress sessions retain their previous cycle linkage; old replacements cannot be reliably distinguished from prior cycle choices. Existing two-day cycles keep their next primary-day suggestion when first used under the new rules. Cycles are local to each routine. Older app builds do not understand the new shared progress and can show or change different suggestions; update all devices before using this version and export a backup first.

The exercise library supports optional, user-defined comma-separated tags, search, tag filtering and reversible archive. Archive hides an exercise from the library's default view but does not remove it from routines, history, or other exercise pickers. Tags and archive status are included in backups and account records; live-device verification remains outstanding. Editing a library entry can add, change or remove its tags.

Workout results use compact lines: shared-weight sets show reps together and mixed-weight sets retain each weight; missing weight is not displayed as zero. During training, up to three recent results appear as three date/result rows. Activity offers one workout history list, filtered by library exercise identity and optional inclusive local dates; it initially shows ten workouts with a control to reveal more, and limits each unfiltered preview to three exercises. The strength chart is optional and reflects the currently displayed matching workouts. Workout details allow result correction. Pagination limits the interface, not the server fetch: the app still loads the whole account workspace.

New workouts retain original plan snapshots, performed order and cycle-history events; old history cannot recover details it never stored. Routine day and slot IDs are assigned when a routine is loaded or saved. New cycle events retain the routine name, day list and pre-event progress; events are not grouped into separate cycle records. Old app builds require server guard migration 005 to prevent them from overwriting newer history. Real Supabase and phone interaction tests are still needed. The online implementation stores separate JSON records and replaces the account's record set atomically per confirmed write, with a 10 MB request limit; storage growth and large histories need performance assessment. A production service worker caches the shell, but account data requires connectivity.
