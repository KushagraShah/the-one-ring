# Setup and current limitations

## Local development

Use Node.js 24 or newer (`.nvmrc` selects 24). Copy `.env.example` to `.env.local` and fill in the Supabase project URL and **publishable** key from the Supabase project's Connect/API Keys settings. `.env.local` is ignored by Git. Run `npm install` followed by `npm run dev`, then open the URL printed by Vite. Restart Vite after changing environment variables. `npm run build` checks TypeScript and creates the production bundle; `npm run preview` serves that bundle locally. `npm run test:config` checks deployment configuration validation.

The app version appears at the bottom of Settings and is sourced from `package.json`; keep `package-lock.json` in sync. The owner requires every pushed change to have a version number, normally a patch increment. Do not create Git tags; the owner is deleting them and does not want future tags. A GitHub Release remains a separate action requiring authorization.

`npm run test:browser` runs Playwright at phone width against a fake Supabase endpoint, not the real project. Install the headless Chromium shell with `npx playwright install --only-shell chromium`, or set `CHROMIUM_PATH` to an existing Chromium executable. On Linux the shell may also need system libraries; `npx playwright install-deps chromium` installs them and may require administrator access. The Pages workflow installs the headless shell and system dependencies and runs these interaction tests before deployment; this does not replace real Android or live Supabase testing. Full Chromium can still be installed with `npx playwright install chromium` if needed for other local work.

## Supabase authentication

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in `.env.local`. Only the current `sb_publishable_…` key format is supported; secret/service-role keys and legacy JWT keys are rejected. If configuration is missing or invalid, sign-in is disabled with a clear message and demo mode remains available.

These values are public browser configuration: Vite embeds `VITE_` values in the downloadable website even if they are stored as GitHub Secrets. Never put a Supabase secret/service-role key, database password, or access token in a `VITE_` variable. Database tables must be protected with RLS, not by hiding the publishable key.

In the Supabase dashboard, enable email/password authentication. Under Auth URL settings, set the Site URL to the deployed URL and allow redirect URLs for the deployed app and local preview (for example, `http://localhost:5173/`). Check email confirmation settings and delivery limits. The owner can disable signup after onboarding and temporarily enable it for a trusted user. First sign-in requires connectivity.

The online-only version requires migration `202611070004_online_workouts.sql`; the Activity/history changes additionally require `202611070005_history_client_guard.sql`. The owner reported applying both on 2026-11-07; live guard behavior has not been independently tested. For any other project, review the [migration runbook](supabase-migrations.md) and verify the target and existing schema before applying SQL. The v0.2.0 deployment used the older local/manual-sync path.

Account workspaces for both mini-apps load from Supabase into memory; changes are saved through a revision-checked transaction. A visible, app-specific saving indicator remains until Supabase confirms all pending changes. The shared account label indicates a signed-in account, not independently verified connectivity. Failures block further editing and offer retry, export of the unsaved in-memory state, or discard and reload. A stale revision requires export or reload. Closing the page before a failed or pending save is confirmed can lose that change. Drafts and unconfirmed edits are not durable. Existing local or old sync data is not automatically imported. Demo is separate in memory and resets on refresh. Supabase Auth may persist its session in browser storage. Live Supabase isolation, real-device handling and backup recovery remain unverified; do not rely on this preview as the sole copy of important data.

The sign-in page, launcher and Settings use a fixed neutral accent; Workout Tracker uses blue and Habit Tracker uses violet. The former accent picker is removed, and any previously stored theme preference is ignored. Existing outcome and status colors are not changed by this palette selection.

### Backup and restore

Settings can export a JSON copy of the current in-memory workout workspace, including exercises, routines, cycle progress, workout history, and confirmed in-progress session data. It does not include credentials, appearance preferences, routine drafts, or unconfirmed result edits. The file contains private workout data; keep it somewhere safe. Export while a save is pending or has failed captures the current in-memory state, which may not yet be on the server.

Restore checks the file and its online record identifiers before asking to replace the current workspace. It then saves the replacement to the current account using the normal revision-checked transaction; wait for the saving indicator to disappear. On a failed save, keep the page open and retry, or export the unsaved state. Demo restore lasts only until refresh. The owner reported successfully exporting, deleting a routine day and restoring; this does not establish every failure or recovery scenario. Fake-server browser tests cover export, validation, failed restore/retry and reload. Backups and the server have 10 MB limits; near-limit files may be rejected by the server after encoding.

## GitHub Pages

The workflow in `.github/workflows/deploy.yml` builds and deploys pushes to `main`. In repository settings, select **GitHub Actions** as the Pages source. Under **Settings → Secrets and variables → Actions**, add repository variables (or secrets if preferred) named `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, using the same public values as local development. The workflow reads a secret first if both exist under the same name, otherwise the variable. Add the configuration **before pushing or rerunning** the workflow; it fails early and leaves the previous deployment in place if configuration is missing or invalid. A change to a variable or secret requires a new workflow run to rebuild the static site.

The expected URL is `https://kushagrashah.github.io/the-one-ring/`; add it to Supabase's redirect allow list and check the Pages deployment workflow. The relative Vite base supports the project path and local preview.

In production, after entering the app, the service worker checks for an update on open and when the page returns to the foreground; Settings also offers **Check for updates**. A waiting update is announced in the app. **Prepare update** activates it without automatically reloading; **Reload app** opens it after a second safety check. The controls block activation and reload while either app has unsaved edits or unconfirmed saves. Workout builder, library, session and Activity screens must be left before updating, because they can contain local drafts. Demo mode must be exited before updating because its data is temporary. Another tab may activate the worker, but this tab never reloads automatically. This protects known in-app drafts and saves, not work in another browser tab; keep each tab's edits safe. Update availability depends on connectivity and browser service-worker behavior. The first registration has no update prompt. The production-shell browser test covers discovery and demo protection; real Android update behavior and signed-in draft/save blocking are not yet independently verified.

The owner removed Supabase's separate GitHub integration after it attempted to apply already existing tables. This does **not** disable the GitHub Actions workflow that deploys the frontend to Pages. Database migrations must be tracked and handled separately; see the [migration runbook](supabase-migrations.md).
