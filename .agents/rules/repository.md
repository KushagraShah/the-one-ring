# Repository rules

Keep persistent context small, current and relevant. Maintain one authoritative home for each fact. Update or remove superseded text instead of appending corrections. Historical logs are local records, never required reading. Governance changes require an explicit user request and Instructor; ordinary application approval is not an exception.

Inspect the working tree before editing and preserve unrelated work. The One Ring has a shared shell plus Workout Tracker, Habit Tracker and Recipe Book. Locate current code through `docs/architecture.md` when needed; old plans and retained experiments are not implementation authority. Keep shared wording app-neutral. Product ideas do not authorize new features or integrations.

Use Node 24+ and check the actual runtime. Commands live in `package.json`; `npm run build` includes TypeScript checking, and there is no separate lint task. For changes with interacting states, assess relevant combinations and adjacent regressions proportionate to risk; review reports all material findings identified in the pass. Choose relevant verification using `one-ring-verify-change`. Inspect test scripts before running them. Finish implementation before routine verification, and report actual checks and material gaps accurately.

Update ordinary docs when behavior or setup changes. Keep `docs/setup.md` operational, `docs/architecture.md` structural, and `docs/app-behavior.md` about current domain behavior. `docs/next-steps.md` is optional local planning, absent from fresh clones; never stage its contents or edit the user's manual notes unless explicitly requested. An authorized removal from tracking may stage its deletion while preserving the local file. Lasting shared facts belong in maintained tracked docs. Link to the authoritative page instead of repeating it. General pages should usually fit 400–800 words; tested runbook examples justify exceptions. Retire completed plans after preserving valid decisions; use Git history rather than a docs archive. Do not maintain an accumulating release narrative.

Write one fresh short ignored task log at completion. Do not read old logs by default. Plans stay in chat unless requested. Protected paths and ownership are listed in `.agents/README.md`; report stale rules to the user instead of editing them as Developer, Manager or Reviewer.

Keep private backups, screenshots, conversion outputs and browser profiles out of Git. The named root `backups/` directory is the local home for private exports and conversion inputs; do not add those files to Git. Never stage `habit-tracker-copy-ref-donotpushtogit/`; it is a private read-only reference, not publishable code. Use ignored root `.tmp/` for agent-created temporary work instead of `/tmp`; remove task-created disposable artifacts after use without deleting unrelated files. Do not create other ad hoc hidden or `*.local` directories at the repository root. This location does not bypass tool permissions.

Only migration files belong under `supabase/migrations/`, using the timestamped naming convention. Do not add standalone SQL check, preflight or verification scripts under `supabase/` or another repository directory. Run one-off SQL in the target SQL editor, or keep a test-only query inside the test that owns it; delete temporary SQL after use. Existing migrations and the SQL examples embedded in maintained runbooks are the authoritative database references.

Use project versions `a.b.c`: increment `a` for a new mini-app or a major app change, `b` for other major changes such as code or data-handling overhauls, and `c` for minor changes, features and fixes. Reset lower levels to zero when incrementing a higher level. This is a project convention, not a SemVer compatibility guarantee; keep package and lockfile versions consistent.

Authorization is task-specific. Do not infer permission to publish, rewrite history, change live systems or access private accounts from an old document. No tags or GitHub Releases without explicit authorization.

Before a deployment-triggering app push, run the locally applicable checks in `.github/workflows/deploy.yml`; if any fail or cannot run, do not push, investigate and suggest a fix. After pushing, watch the run for the pushed commit with `gh run watch <run-id> --exit-status` and report its outcome; investigate failures and suggest a fix. If no deployment is triggered or its outcome cannot be verified, say so.
