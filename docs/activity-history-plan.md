# Activity and workout history: proposal for review

This is a proposed direction, not implemented behavior. The owner requested research and a detailed plan before deciding on Activity and history changes. Account data remains online-only; manual backups remain the recovery option.

## Current behavior and gaps

- `WorkoutStats` shows total workouts, a rolling 28-day count, and results for an exercise selected from completed history. Activity shows a list of workouts and allows editing only the latest workout's completed results. There are no charts or per-workout detail screens.
- Exercise history groups new results by stable exercise ID, with name fallback for older records. An old name alone can be ambiguous. Current code displays blank weight as `0` in several places, which can misrepresent unknown or bodyweight values. The 28-day count has no upper bound, and the all-time count also includes early-finished or all-skipped workout records; define a label and counting rules rather than implying every entry represents training.
- Finished workouts store a day name, completion timestamp, performed exercise names/IDs, sets, cardio, notes and skip flags, and sometimes the original planned name/ID for substitutions. They do not reliably store routine ID/name, day ID, initial ordered slots, original selected cycle variant, start time, actual versus planned order, exercise source, equipment snapshot, or routine-cycle/explicit skipped-day history. Replacements and extras cannot always be distinguished later. Changing a routine or library entry must not rewrite earlier context.
- Day and session operations use names in places; names are not sufficient stable identifiers. Cycle progress is updated at workout finish; ordinary substitutions, extras and skips do not advance exercise cycles, while an out-of-order cycle selection leaves earlier unperformed variants due. Existing free workouts and finish-early behavior must remain valid.
- The active implementation stores per-entity JSON records using a single revision-checked, whole-workspace transactional RPC. The earlier normalized tables are not the live source of truth. Each write replaces the record set and has a 10 MB request limit; extra snapshot size and request cost should be measured. No backend migration is automatically required for additive JSON fields, but schema changes to the RPC or new record kinds would need a reviewed migration.

## Proposed phone-first Activity

1. Keep **Activity** as a single entry point. Start with a concise recent-workouts list and a small 28-day count. Tapping a workout opens a detail view showing its date, routine/day when known, completed, skipped and unfinished items, and clearly labeled substitutions/extras. Keep a straightforward path back to the list and the existing latest-result editing behavior. Decide separately whether editing older workouts is wanted; do not silently expand it.
2. Add a prominent **Exercise progress** action: select one specific library variant, including archived variants with prior results. Show a compact chronological list of actual three-set results and notes first; expose one focused chart only when there are sufficient comparable values. A rename retains the same ID; a different machine is never combined just because its name matches. Legacy name-only records remain visibly legacy/ambiguous unless uniquely and safely linked.
3. Initial strength chart proposal: recorded top working-set weight by session, with the reps achieved alongside every point; show the full three sets in the nearby list. This is a measurement, not a strength score. At the same weight, rep changes are visible in the list. Do not treat an empty weight as zero; omit it from the weight chart and display it as not recorded. If all weights are blank, show reps/history instead. Different set weights are individually retained. A heavier single set is not automatically evidence of overall progress.
4. Cardio: keep duration, speed and incline in **degrees** visible per result; if charting initially, allow one chosen metric at a time and do not invent distance or convert degrees into percent. Missing values remain missing. For both types, use actual dates and deterministic ordering for multiple sessions on one day, show empty/one-result states, and keep a textual accessible equivalent with no reliance on color or hover. Avoid estimated 1RM, composite scores, cross-machine comparisons and training advice by default.
5. Count policy proposed for review: count workout sessions containing at least one completed strength or cardio result as training; label an all-skipped or empty early-finished session as such instead of counting it as a completed training workout. Define local-day boundaries explicitly for the rolling 28-day view and exclude future records. Preserve all sessions in the history list regardless of summary count.

## Proposed history capture

1. Give newly created routine days and planned slots stable IDs. Existing routines get IDs through a deterministic, tested upgrade where possible, saved on an ordinary revision-checked write; retain legacy names as display snapshots. Do not guess links where names are ambiguous. Confirm how routine cloning and slot reordering preserve or create identities.
2. On starting a session capture: session ID and start timestamp; free-workout vs routine source; routine/day IDs and names; ordered planned slots; and, for cycle slots, cycle ID/name, suggestion and relevant member identity. Snapshot fields remain historical even when routine/library names or setup later change. Capture only relevant setup/equipment snapshot fields, not an unbounded copy of the library.
3. Maintain separately ordered performed items with their own IDs, linkage to the original slot where applicable, actual exercise ID/name/equipment snapshot, source (`planned`, cycle selection, substitution, extra), status (completed, skipped, unfinished), actual values and notes. Reordering during training does not alter planned order. Repeated replacements retain the **original** planned slot. Completing a cycle member through its selector versus an ordinary substitution must remain distinguishable.
4. Finish records the finish timestamp and commits the workout, routine progress and exercise-cycle progress together through the existing checked server transaction. Cancelling remains a discard and does not advance cycles. Finish-early records unfinished separately from skipped. A free workout has no routine/day/plan, and extra exercises remain extras. Existing result editing should update performed data without rewriting the initial plan or automatically re-advancing cycles.
5. Record routine-cycle progress events sufficiently to distinguish an explicit skipped day, actual workout completion, reset, and rollover. Prefer a bounded record per cycle with day snapshots and close reason over an event-sourcing framework. Store ordered historical facts alongside current progress, and make day skip/reset updates atomic with the progress change. Do not silently count a skip as a workout.

## Compatibility and rollout

- Add optional versioned fields first, retain support for existing backup format and active sessions, and provide fixtures for old and new data. Explicitly display `Not recorded` for unavailable historical fields; never infer old routine, start time or plan from today's routine. Existing name-only performance records remain a clearly identified legacy fallback.
- Update `parseBackup`, restore preparation, online projection/readback and schema tests to retain new fields and reject malformed input without losing data. Export/restore must preserve both old and new records. Test old-client behavior: an older deployed PWA can strip unknown fields when rewriting records. Plan a client-version gate or coordinated upgrade before trusting new snapshots; do not assume that additive JSON fields alone protect them.
- Keep RLS and owner scoping, revision conflict handling and atomic writes. Avoid SQL until the existing record format is sufficient or a concrete migration is designed. If changing SQL, review target schema/migration history, test in disposable projects and provide the owner a file to run; do not silently reset data.
- Build and verify in phases: (A) stable IDs and forward-compatible snapshot model plus tests; (B) session/cycle capture and compatibility; (C) Activity list/detail and exact-variant text history; (D) a minimal chart once comparable values and semantics are approved. Keep old history accessible throughout. No new screens or schema changes have been authorized by this proposal alone.

## Acceptance and test cases

- Routine and library rename, edit, reorder and archive do not change old snapshots; different machines with similar names remain separate. Legacy records with missing IDs do not acquire invented certainty.
- Free, planned, skipped, partial/early-finished and all-skipped workouts; cycle A then C suggests B; skip, ordinary replacement and extra do not advance; cancel does not advance; repeat an accounted variant; reset and rollover; multiple routines; linked cycle slots; repeated substitution and session reordering.
- Strength with shared/different/blank weights, zero reps and mixed valid data; cardio with missing optional fields and incline degrees; no comparisons across variants. Stable chronological ordering, same-day entries, day boundaries, future records, long gaps and one/no-data chart states.
- Export/restore across old/new formats and active sessions, malformed/duplicate IDs, revision conflict, failed/lost-response retry, account isolation and demo separation. Verify snapshot plus cycle transition remains atomic. Measure growth and the 10 MB limit with synthetic data.
- Unit tests for selectors and calculations, real browser tests for user flows and accessible table, phone-width layouts, and explicit manual Android/live-Supabase checks before claiming complete verification.

## Research informing the proposal

- [Hevy exercise performance](https://www.hevyapp.com/features/exercise-performance) illustrates individual-exercise histories and separate weight/rep/volume metrics; those are examples, not a mandate to replicate its features.
- [Resistance-training load review](https://pmc.ncbi.nlm.nih.gov/articles/PMC7927075/) distinguishes load and volume load and cautions against treating one number as a complete measure. [NASM's 1RM calculator](https://www.nasm.org/resources/one-rep-max-calculator) describes estimates and their assumptions; the app need not infer a 1RM from ordinary three-set logs.
- [US Web Design System: data visualizations](https://designsystem.digital.gov/components/data-visualizations/) recommends labeled graphics with accessible textual equivalents.
- [Microsoft: Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing) describes significant complexity and tradeoffs; simple versioned workout and cycle snapshots are preferable here unless requirements change.
