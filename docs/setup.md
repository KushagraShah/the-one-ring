# Setup and current limitations

## Local development

Use Node.js 22 or newer. Copy `.env.example` to `.env.local` and fill in the Supabase project URL and **publishable** key from the Supabase project's Connect/API Keys settings. `.env.local` is ignored by Git. Run `npm install` followed by `npm run dev`, then open the URL printed by Vite. Restart Vite after changing environment variables. `npm run build` checks TypeScript and creates the production bundle; `npm run preview` serves that bundle locally. `npm run test:config` checks deployment configuration validation.

`npm run test:browser` runs the Playwright browser interaction test against a fake Supabase endpoint; it does not contact the real project. Install Playwright's Chromium with `npx playwright install chromium`, or set `CHROMIUM_PATH` to an existing Chromium executable (for example, `/snap/bin/chromium`). The test exercises the existing local preview, not an RxDB implementation.

The RxDB workspace and migration `202611070003_rxdb_workout_workspace.sql` are **prototypes, not integrated into the UI**. Do not apply the migration yet. The app still uses the experimental localStorage/IndexedDB sync described below; the RxDB prototype is not a finished sync replacement.

## Supabase authentication

Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in `.env.local`. Only the current `sb_publishable_…` key format is supported; secret/service-role keys and legacy JWT keys are rejected. If configuration is missing or invalid, sign-in is disabled with a clear message and demo mode remains available.

These values are public browser configuration: Vite embeds `VITE_` values in the downloadable website even if they are stored as GitHub Secrets. Never put a Supabase secret/service-role key, database password, or access token in a `VITE_` variable. Database tables must be protected with RLS, not by hiding the publishable key.

In the Supabase dashboard, enable email/password authentication. Under Auth URL settings, set the Site URL to the deployed URL and allow redirect URLs for the deployed app and local preview (for example, `http://localhost:5173/`). Check email confirmation settings and delivery limits. The owner can disable signup after onboarding and temporarily enable it for a trusted user. First sign-in requires connectivity.

**Authentication alone is not workout sync.** Data is stored separately for each account and the demo. In the local development version, use Settings → Cloud sync to set up experimental automatic sync explicitly; existing cloud data is never silently imported over local data. After setup it tries while the app is open, when changes are made, on reconnection or return to the foreground, and periodically. A status button opens Settings; conflicts require a choice and manual retry remains available. Incoming changes wait until the user leaves a workout, routine/library editor, or Activity. This is not operating-system background sync and does not run with the app closed. The previous release's manual sync worked between the owner's laptop and phone; the new automatic behavior, real Supabase conflicts and account isolation, and Android/offline restart remain unverified end to end. Local browser data can be cleared or evicted; export a backup and do not rely on this as the sole copy.

## GitHub Pages

The workflow in `.github/workflows/deploy.yml` builds and deploys pushes to `main`. In repository settings, select **GitHub Actions** as the Pages source. Under **Settings → Secrets and variables → Actions**, add repository variables (or secrets if preferred) named `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, using the same public values as local development. The workflow reads a secret first if both exist under the same name, otherwise the variable. Add the configuration **before pushing or rerunning** the workflow; it fails early and leaves the previous deployment in place if configuration is missing or invalid. A change to a variable or secret requires a new workflow run to rebuild the static site.

The expected URL is `https://kushagrashah.github.io/the-one-ring/`; add it to Supabase's redirect allow list and check the Pages deployment workflow. The relative Vite base supports the project path and local preview.

The owner removed Supabase's separate GitHub integration after it attempted to apply already existing tables. This does **not** disable the GitHub Actions workflow that deploys the frontend to Pages. Database migrations must be tracked and handled separately; see the [migration runbook](supabase-migrations.md).

## Current preview

The app has demo mode, accent colors, an exercise library and multiple local routines, balanced day suggestions, rotations, three-set strength and cardio logging, basic workout/exercise history, and local JSON export/restore. Workouts shows the suggested day and first exercise near the top. During a workout, the focused exercise shows setup and up to three recent results; previous/skip/next controls navigate the session, skipping advances to the next exercise, and the last exercise offers a return to the first. An exercise may be replaced or added for today without changing the routine; both appear in the current session navigation. Setup notes use a multiline editor and preserve text including Markdown syntax. Leaving a workout keeps confirmed results for resumption; cancelling it explicitly discards the session. Strength entry offers shared weight adjustments and rep presets, with custom set fields available. A confirmed log is locked until edited; the workout finishes automatically when every exercise is completed or skipped. The latest workout's results and notes can be edited in Activity, including after automatic completion; adding an extra exercise after automatic completion is not yet supported. Unconfirmed result edits stay in memory while navigating the session and are not saved until the tick; leaving warns before discarding them. Notes are saved separately. Backups receive structural validation before restore, but recovery under storage failures and browser/device changes has not been tested end to end. The sample routine and initial demo progress are illustrative. New history records use stable exercise IDs; older name-based records are linked when an exercise is renamed. This local migration still needs wider real-world testing, and older ambiguous names cannot be recovered automatically.

In **Workout Tracker → Build routine**, choose a routine, expand a day, and edit or reorder its exercises using the up/down controls. Changes are a temporary draft until **Save changes**; leaving warns before discarding, but drafts are not durable across a browser crash. An active workout blocks saving or switching routines; it can be cancelled from the builder without discarding the draft. Create an exercise cycle from an exercise, choose its variants and one or more days, or add an existing cycle to another day. The cycle editor indicates whether each selected day uses an existing exercise slot or adds a new one. All linked days share progress. During a workout, choose a different member using the dedicated **Exercise cycle** selector; completing that member counts toward the cycle. The separate ordinary replacement and extra-exercise controls do not count toward it, even if the chosen exercise happens to be a member. Completing A then choosing C out of order leaves B as the next suggestion; once every variant has been performed, the cycle starts again. Repeating an already-accounted variant or skipping does not advance it. Cycle progress is committed when the workout is finished, not separately when a log is ticked; cancelling a workout leaves it unchanged. Existing in-progress sessions retain their previous cycle linkage; old replacements cannot be reliably distinguished from prior cycle choices. Existing two-day cycles keep their next primary-day suggestion when first used under the new rules. Cycles are local to each routine. Older app builds do not understand the new shared progress and can show or change different suggestions; update all devices before using this version and export a backup first.

The exercise library supports optional, user-defined comma-separated tags, search, tag filtering and reversible archive. Archive hides an exercise from the library's default view but does not remove it from routines, history, or other exercise pickers. Tags and archive status are included in local backups and the existing experimental sync projection; live-device verification remains outstanding. Editing a library entry can add, change or remove its tags.

Reordering routine days, comprehensive planned-versus-performed snapshots, cycle snapshots and historical skipped-day records, and comprehensive backup recovery remain incomplete. Substitute records retain the original exercise name/ID, but this does not reconstruct old records or retain a complete routine snapshot. The UI still writes localStorage and projects changes asynchronously into IndexedDB; this is not one atomic local database transaction. Workout completion now journals the workout and cycle writes so an interrupted commit can finish on reload. Other multi-key writes, storage eviction, old-client upgrades and recovery still need work. Avoid editing the same account in multiple tabs: if another tab writes local data, sync stops and asks for a reload, but this is not a cross-tab editing lock. Automatic syncing is experimental, runs only while open, and has not been validated on live devices. A production service worker caches the app shell and install icons, but offline authentication and launch have **not** been verified on Android; the manifest and worker do not guarantee installation or safe persistence. See the [migration runbook](supabase-migrations.md) before applying migrations to another project.
