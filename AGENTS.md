## Commands and verification

- Use Node **24+** (`.nvmrc`, package engines and CI agree); check the actual shell version. An older local Node 20 shell previously needed `--experimental-websocket` for the Supabase client test; prefer the supported runtime.
- Local setup: `npm ci`, copy `.env.example` to `.env.local` only if missing, then `npm run dev`. Restart Vite after environment changes. `npm run build` runs TypeScript checking before bundling; there is no separate lint/formatter task.
- `npm run test:config` checks deployment/UI conventions and generated avatar previews. `npm run test:history` runs domain, backup and store tests; `npm run test:schema` runs migrations in embedded PGlite without a Supabase service.
- Focus a TypeScript test with `node --import tsx --test tests/recipes.test.ts`; filter names with `node --import tsx --test --test-name-pattern='pattern' tests/recipes.test.ts`. SQL/config tests use `node --test tests/recipe-schema.test.mjs`.
- Browser checks: `npm run test:browser -- tests/browser/<file>.spec.ts -g 'pattern'`. Playwright starts its own Vite server at **127.0.1.1:4179**, with mock Supabase configuration and no existing-server reuse. These tests use demo/fake services.
- Install Chromium with `npx playwright install --only-shell chromium`, or set `CHROMIUM_PATH` to an installed executable (also honored by PWA tests). Linux browser libraries may need `npx playwright install-deps chromium`.
- **Build before `npm run test:pwa`**: it reads `dist/` and launches Chromium for production update tests. `sw.js` is generated by the Vite build; edit `vite.config.ts`, not `dist/sw.js`.
- Finish implementation before routine verification; run targeted checks once near the end. Documentation-only edits do not need a local full build. Pages CI runs config → schema → domain/store → browser → build → PWA checks.
- Avatar source is `src/assets/avatars/portraits.svg`; after editing it, run `npm run avatars:generate` to refresh tracked standalone SVGs. See [artwork provenance](src/assets/README.md).

## Wiring and persistence

- `src/main.tsx` mounts `AppDialogProvider` → `AuthGate` → identity-keyed `src/app/App.tsx`. The shell keeps all three app workspaces mounted and coordinates navigation, sign-out, backups and update guards through their handles; preserve those guards when changing navigation.
- Active storage is in each mini-app's `online.ts`. Workouts serialize a whole record set through `workspace.ts`; habits and recipes each replace one JSON workspace. Each app has its own revision and atomic write, with a **10 MB** server request limit. Full restore spans separate writes and can partially complete.
- Supabase is authoritative; account data is held in memory, demo resets on refresh, and browser storage is for Auth/preferences. Do not activate `src/workout/legacy-sync/`, import old local/demo data implicitly, or treat the normalized [workout data model](docs/workout-data-model.md) as the deployed schema.
- Preserve owner checks, stale-revision rejection and stable operation IDs/request bodies on retry after an uncertain response. Errors/conflicts retain unsaved memory for export/recovery; drafts are not crash-durable. UI pagination does not reduce whole-workspace fetches.
- Username/avatar live in Supabase Auth user metadata, outside app backups and the workspace revision protocol. Signup stays open during development by owner decision; do not change Auth settings without authorization.
- Environment keys are `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; only `sb_publishable_…` keys are supported. All `VITE_` values are public in the bundle. Never use secret/service-role keys, passwords or access tokens there.
- The service worker caches the production shell, not account data. Update activation/reload is user-controlled and guarded against drafts, pending saves and demo loss; preserve both safety checks.

## Product rules easy to regress

- No new expanding/collapsing sections, native select dropdowns or JavaScript alert/confirm popups. Reuse `ChoiceSelect`, `DetailView`, `AppDialog`, `ConfirmDialog`, `CloseButton` and `InfoTip`. Browser date/month/file pickers and before-unload warnings remain browser-controlled.
- In-app actions use touch-sized buttons and labeled icons; close uses ×. Preserve discard/destructive confirmations, including workout cancellation. Actual external references may remain links. Do not restore workout exercise swiping or session move-earlier/later controls.
- Preserve shared forest/gold surfaces with neutral shared, blue workout, violet habit and terracotta recipe accents; there is no user accent picker. Keep the mobile app-ring strip with fixed Home/Settings and the desktop list of available apps.
- **Workouts:** exact machine/variant identity owns history; do not compare raw weights across machines. New strength logs save three sets plus the note in one action (legacy two-set results remain editable); setup saves separately, treadmill incline is degrees, and one date applies to the whole workout.
- Routine drafts and session substitutions/extras are distinct. Keep plan snapshots and performed order. Finishing is explicit even after all exercises are accounted for; only finish commits cycle progress. Cycles share progress across linked days within a routine: A then C still suggests B. Only completed dedicated cycle selections count; skips, ordinary replacements and extras do not. Historical corrections do not recalculate cycles.
- **Habits:** rules/labels are date-effective; unlogged is not Missed. Intentional skip is a one-day pause, excluded from fixed score/coverage/streak length and flexible-week judgment. Outcomes save immediately and tapping again unlogs while retaining notes; notes save on blur/close. Fixed score is `(Done + 0.5 × Partial) / scored outcomes`; keep flexible targets separate.
- **Recipes:** plans, shopping and cooking keep independent snapshots when sources change/delete. Legacy parsing/step indices remain compatible until explicit conversion. Quick glance and nutrition are authored, not generated; totals require complete portion values and shopping text is not automatically scaled. Detail/editor/full-cooking-recipe use separate styled dialogs, full-screen on phones.

## Completing work

- Update relevant docs when behavior/setup/verification changes and append a concise dated entry to [docs/agent-logs.md](docs/agent-logs.md). Keep this file durable and README short.
- The owner authorizes committing/pushing/deploying completed work by default unless they request local-only work. **Version every push**, including documentation: update `package.json` and both root version fields in `package-lock.json` together. Smaller changes increment patch; major existing-app updates increment the middle number; a new mini-app or major framework overhaul increments the first. Honor an exact owner-specified version.
- Verify the successful Pages workflow, exact deployed commit and live package version after pushing. Do not create tags or a GitHub Release; releases require separate authorization. Published history must not be rewritten without explicit authorization.
- Never stage `habit-tracker-copy-ref-donotpushtogit/`: it is an untracked, read-only reference supplied by the owner, not code to copy or publish. Keep backups, feedback screenshots, conversion outputs and personal records out of Git. Use ignored `*.local` directories inside this repository for temporary work.
