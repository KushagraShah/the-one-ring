# Recipe Book: local first implementation

## Purpose and decisions

The owner creates precise vegetarian, macro-aware meal-prep recipes outside the app with AI tools. The app is not an AI recipe generator, meal diary or nutrition authority. It should support a personal collection, explicit shopping and cooking phases, fixed portions, metric ingredients and authored per-portion macros. A pantry inventory, images, web importing, automatic nutrition calculation, scaling, offline sync and sharing are not in scope. No real recipe examples were supplied; demo examples are fictional.

Recipe, Shopping and Cooking are separate, freely accessible views. Opening a library recipe shows a styled, independently scrollable dialog, full-screen on phones, rather than resizing a library card; × and Escape close it. Shopping snapshots the source recipes and keeps per-recipe ingredient items, not guessed combined quantities. Add recipes without clearing the list; edit/remove individual list items without changing the saved recipe. Items stay in place with clearly labeled Have/Bought actions, a Need reset, visible status and a summary; no persistent pantry inventory. Cooking snapshots the chosen recipe and saves a current step. Both phases warn when a saved source changes or is deleted, without silently changing the active copies; cooking can explicitly restart from an updated recipe after confirmation. Older shopping snapshots have no source identities and explicitly say changes cannot be checked. View full recipe uses a separate styled dialog, full-screen on phones. Both phases can be resumed after closing once online saves are confirmed. Ending a phase is confirmed.

Review shows extraction warnings when applicable, and a compact macro reminder when ingredients or portions change without a macro update. Recipe confirmations name the actual action, while Cancel leaves the operation unperformed.

The local preview uses the shared dark forest and aged-gold surfaces with a fixed warm terracotta (`#efaa89`) recipe accent throughout the shell and cookbook views. The book-spine heading, selected page tabs and recipe cards retain a distinct cookbook character. The color revision is for owner review; it does not change the established workout or habit palettes.

## Markdown and fidelity

The template uses a `#` title, optional `Portions:` and `Macros per portion:` lines, and `## Quick glance`, `## Ingredients`, `## Pantry`, and `## Instructions` sections. Quick glance is authored Markdown displayed during cooking, not a generated summary; older recipes without it show an explicit empty state. Ingredient bullets and numbered instruction lines are extracted; indented bullets or numbered lines retain legacy extraction behavior and produce a warning. Original Markdown remains intact; recipe details and the full cooking recipe render Markdown, including tables, without executing raw HTML or loading external images. Add/edit opens its own styled window, full-screen on phones, with review as a separate view in that window; × and Escape retain the discard confirmation. Parsing is deliberately conservative: review extracted data and warnings before saving, with a return to the retained draft; never infer quantities, macros or units. Unsupported lines in recognized sections are warned, but unsupported headings cannot always be identified, so review remains essential. Editing prompts review of authored macros. Phase snapshots do not change on edits.

## Implementation and safety plan

1. Add an independently owned recipe workspace, revision-checked Supabase RPC and a local-only migration; do not apply it without explicit owner authorization. Demo remains in memory. Account preview requires that migration; no demo data enters accounts.
2. Add a distinct mobile-first recipe app, import review, library, shopping checklist, cooking step navigation and deliberate completion. Preserve authored Markdown and show structured extraction without rendering unsafe HTML.
3. Integrate launcher, app switching, sign-out and update draft/save guards. Recipe-only export/restore and a three-app full backup (format 2) include active phases. The separate workout/habit backup retains format 1 compatibility. Full restore validates first but each app saves separately and may partially complete. Older recipe previews may drop the optional shopping-source snapshots; do not use them to edit newer data without further compatibility safeguards.
4. Validate workspace/restore data, revision conflicts, retries and snapshots; exercise parser and core interactions using demo/fake service. Do not claim live Supabase, real device or offline verification. Show loading/error and recovery; no SQL execution against the real project.
5. Owner reviews the local preview. Refine interaction, import format, full-backup integration, migration application and real service safety before any deployment.
