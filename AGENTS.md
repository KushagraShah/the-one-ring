## Workout requirements and decisions

- A reusable, personal, equipment-specific exercise library is central. A different machine or meaningful variation has a separate identity and history. Keep machine setup, brief instructions, reference links and exact-variant history close to logging; the same variant can be reused across routines/days. Metadata is optional supporting information, not the center of the workflow.
- Make **building routines** and **doing a workout** clearly distinct. Multiple named routines and ordered days should be possible. A routine guides rather than restricts: allow free workouts, substitutions, navigation in any order, skips and extras without silently changing the saved routine. The owner explicitly requested removal of the session's move-earlier/later controls; existing reordered sessions and historical order must remain intact. Preserve planned versus performed information and historical snapshots.
- The owner's current routine is Push, Pull, Accessories and Legs, typically trained two or three times per week rather than on fixed days. A routine **cycle** balances the days: suggest the first remaining day even after an out-of-order workout; allow explicit skips and resets. Each routine should remember its own progress.
- Exercise cycles are **independent**, not global Notion-style rounds. A cycle can appear on one or multiple days and shares progress across those slots. A completed member chosen through the cycle selector counts; an out-of-order choice must not skip the remaining earlier suggestion (A then C suggests B). Skips, ordinary replacements and extras do not advance it, even when they happen to be cycle members. Current local behavior and limitations are in `docs/setup.md`.
- Strength entry normally uses one weight and three rep values, optionally different weights per set. The owner considers an exercise atomic: either zero or three sets, with **one completion action per exercise**, not a checkbox for each set. Keep subjective notes and show the exact variant's previous performance. Cardio needs suitable fields; the owner's treadmill incline is in degrees.
- The owner does not need a warmup checklist during training. Focus the phone interface on the exercise being performed, with setup and several recent results close to entry. Save and lock a three-set result with one tick, with separate notes and setup. The workout remains open after all exercises are accounted for so notes or extras can be added; finishing explicitly commits cycle progress. Better per-exercise and overall insights are a major goal; do not compare raw weights across different machines or invent a composite score.
- The old Notion setup is a source of useful ideas (canonical exercises, setup notes, related logs, rotations), not a UI or rigid schema to replicate. It became too dense and inflexible. No in-app Notion importer is required now; a one-time migration may be considered later.

## Required working practices

**Version every push.** Follow the owner's project-specific convention, not standard semantic-version labels: `0.A.x` increments `x` for smaller updates; `0.X.0` increments the middle number for a major update; `X.0.0` increments the first number for a new mini-app or a major framework overhaul. Assess the actual scope and choose a logical version; use an exact version when the owner specifies one. For each new pushed change, update the version in both `package.json` and `package-lock.json`; Settings displays the package version. Verify the version and deployment together. A version number does not itself authorize creating a Git tag or GitHub Release; never move an existing published tag. Do not rewrite published history or force-push without explicit authorization; the owner explicitly authorized the specific v1.0.0-to-v0.6.0 correction.

**Release tagging practice.** For each authorized deployment, verify the Pages workflow succeeded and identify its exact deployed commit. Subject to authorization for tag creation, create and push an annotated `v<version>` tag pointing to that commit; do not tag a failed deployment as live. A GitHub Release page with short notes is useful for major updates but is separate and optional, subject to authorization. Never move an existing published tag; correct mistakes with a new commit and version. Do not backfill old tags without verifying their exact commits and authorization, particularly for corrected deployments. Keep tagging a deliberate post-deployment action rather than adding automated workflow permissions. The owner requested documentation of this practice; v0.7.0 remains untagged unless tag creation is separately authorized.

1. **Own the task through completion.** Implement and verify what was requested; don't stop at a partial increment or repeatedly ask for obvious next steps. Make small, reversible product decisions yourself. If a consequential requirement is unclear, or an external action is genuinely needed, stop and ask the owner with clear instructions; never ask for credentials in chat. Be honest about blockers, partial results and unverified behavior.
2. **Be efficient without skipping correctness.** Choose targeted checks during development and run an appropriate final test/build once, rather than repeatedly rebuilding. Docs-only work generally does not need a full build. Do not venture outside this repository for project work; use an ignored temporary directory inside it if needed. Follow the harness's tool and permission constraints.
3. **Maintain documentation as part of every completed task.** Update the relevant docs and this handoff when behavior, setup, architecture, verification or limitations change. Keep the root README short and human-oriented; do not state planned functionality as implemented.
4. **Append to [`docs/agent-logs.md`](docs/agent-logs.md) after each task.** Add a brief dated summary of changes, verification, and important limitations or external actions. Preserve previous entries, keep it concise, and never include secrets or personal workout data.
5. **Check Git, deployment and release state.** Inspect `git status`, relevant deployment results and tags as appropriate; aim to leave Git clean and clearly report anything pending or unverified. Never discard another person's work to make it clean. Commit, push, deploy, or create release tags only when authorized; report local changes or a blocked credential prompt rather than silently leaving work behind. Don't rewrite history or force-push without explicit authorization.
6. Preserve user data and unrelated work. Avoid silent destructive migrations, implicit demo-to-account imports or last-write-wins sync. Ask before consequential external or destructive operations. If access or tooling is unavailable, explain what was checked and what the owner needs to do.
